# Rewrite Rules

The rules below are **non-negotiable**. Every rewrite, suggestion, and report
generated by this skill must follow them. When a rule conflicts with what the
user asks for, the rule wins — explain the conflict and offer the closest
honest alternative.

---

## 1. Never fabricate facts

Do not invent, infer, or "round up" any of the following:

- Companies, employers, clients, or schools
- Job titles or seniority levels
- Employment dates, durations, or gaps
- Degrees, certifications, GPAs, honors, or awards
- Publications, patents, talks, or open-source projects
- Tools, languages, or frameworks the user did not list
- Locations, team sizes, budgets, or headcounts
- **Metrics** — percentages, dollar amounts, latencies, throughput, user
  counts, conversion rates, model accuracies, etc.

If a bullet has no metric and the original text gives no honest basis to
infer one, **do not add one**. Rewriting a vague bullet into a stronger
*qualitative* bullet is correct. Inventing a number to make it look strong is
not.

## 2. Mark every assumption

When a rewrite depends on something the user must confirm, surface it inline:

> **[CONFIRM]** Suggested rewrite assumes the migration shipped to
> production. If it was a proof-of-concept, use the alternate version below.

Two acceptable labels:

- `[CONFIRM]` — claim is plausible but the user must verify before using it.
- `[ADD IF TRUE]` — a placeholder for a metric, scope, or outcome the user
  may have but didn't include. Example:
  `Reduced p99 latency by [ADD IF TRUE: X%] by introducing Redis caching.`

Never silently fill these in.

## 3. Preserve voice and seniority

- Match the user's tense (past for past roles, present for current).
- Match formality. A research CV stays formal; a startup engineer's resume
  stays direct.
- Do not promote the user. "Engineer II" does not become "Senior Engineer."
  "Contributed to" does not become "Led" unless the source text supports it.

## 4. One verb per bullet, strongest first

- Start every bullet with a strong action verb (see [action-verbs.md](./action-verbs.md)).
- No "Responsible for…", "Worked on…", "Helped with…", "Assisted in…".
- One bullet = one accomplishment. Split compound bullets.

## 5. Prefer structure over adjectives

- "Robust, scalable, mission-critical" tells a recruiter nothing. Show the
  result instead — request rate, customer count, uptime, latency, dollars.
- Use the bullet formulas in [bullet-formulas.md](./bullet-formulas.md) (X-Y-Z,
  CAR, STAR) as scaffolding when the source bullet lacks structure.

## 6. ATS-safe by default

When rewriting structure (not just bullets), follow [ats-rules.md](./ats-rules.md):

- Single column, no tables for layout, no text boxes, no icons standing in
  for words, no headers/footers carrying important content.
- Plain section headings: `Experience`, `Education`, `Skills`, `Projects`.
- Dates in a parseable format (`May 2023 — Aug 2024`).
- File format: `.docx` for ATS submission, `.pdf` only when the posting
  explicitly accepts it.

## 7. Tailor, don't pad

When optimizing for an inferred target role:

- Pull keywords from the relevant file under [keywords/](./keywords/) **only
  if the user has the underlying experience**. Adding "Kubernetes" because
  the role mentions it, when the user has never touched it, is fabrication.
- Reorder, re-emphasize, and re-word what the user *does* have so the
  relevant experience surfaces first.

## 8. Cut before you add

Default to a shorter resume:

- One page for <8 years experience, two pages otherwise. Research/academic CVs
  are an exception.
- Drop high-school details once the user has a degree.
- Drop unrelated jobs older than ~10 years unless they materially support the
  target role.
- Drop generic skill-bullet padding ("Microsoft Word, teamwork, communication").

## 9. Grammar and consistency

Apply [grammar-style.md](./grammar-style.md):

- Parallel structure within a section.
- Numbers: digits for ≥10, words for <10, except metrics (always digits).
- Oxford comma on.
- No first person ("I"), no articles at bullet starts ("The", "A").

## 10. Report what changed

Every rewrite is accompanied by the report defined in
[report-template.md](./report-template.md). The user must be able to see, for
each change: what was before, what is after, and why it improves the resume.
A silent rewrite is a failed rewrite.
